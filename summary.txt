## Combined Summary

This lecture picks up from earlier material on arithmetic expression trees, recursive evaluation, and lexing/parsing, using that foundation as a springboard into Haskell program structure and, more centrally, into how a purely functional language handles input/output (I/O). It begins with the basics of compiling a Haskell program: the `main` function serves as the program's entry point, illustrated with a simple "Hello World" example using `putStrLn`, compiled via GHC.

The lecture then confronts a core tension: Haskell is purely functional and thus, in principle, cannot have side effects, yet real programs need to read input, write output, and interact with disks, networks, and devices. An interactive "Hello World" example using `getLine` exposes this apparent conflict, since operations like reading input seem to violate referential transparency (the guarantee that a function called with the same arguments always returns the same result).

Haskell resolves this conflict through **monads**, and specifically the `IO` monad, which can be understood by analogy to a state monad. The key conceptual trick is to model I/O as threading an implicit "world" state through the program: conceptually, `IO a` behaves like a function `Welt -> (a, Welt)`, where each action consumes the current world and produces a new one, which must be passed to the next action — this enforces a strict, controllable order of execution while keeping the language pure. Sequencing of IO actions is expressed via two composition operators: `(>>)` for running two actions in sequence (discarding the first's result) and `(>>=)` for chaining actions where the second can use the value produced by the first. These monadic operations are generic — they work for any type in the `Monad` type class, not just `IO` — and side effects are visible directly in type signatures, distinguishable by kind, with explicit control over ordering. Although Haskell's `do`-notation offers convenient syntactic sugar for working with monads, it is not essential to the concept; monads can be (and are) used in other languages without special syntax.

The `do`-notation itself is explained in detail: each line is an expression of type `IO a` (or more generally `Monad m => m a`), and the overall `do`-block takes the type of its last action. A layout rule determines block structure — the first non-whitespace character after `do` sets the indentation level for all subsequent actions, and the block ends when a line moves further left. Results of IO actions can be bound using the left arrow `<-` (or ignored via `_ <-` or by omitting binding altogether), and the final action in a block has no arrow, since it represents the result of the whole block. Ordinary functional constructs like `where` and `let` can be freely combined with IO code inside a `do`-block; `let` in this context obeys the same rules as elsewhere (layout, pattern matching, mutual recursion) and is used to introduce purely functional local definitions, much as in list comprehensions. Crucially, a `do`-block is itself just an expression of type `IO a` (or `Monad m => m a`) — it is not a special control structure — and it is automatically desugared into nested applications of `(>>)` and `(>>=)`, which is how the "world"-threading is actually realized under the hood. This desugaring mechanism generalizes beyond `IO` to any `Monad` instance. The program's `main` function, of type `IO ()`, is the ultimate entry point that sequences built-in and user-defined IO actions together.

A recurring stylistic principle is the separation of pure functional code (e.g., a function like `reverseWords`) from I/O code with side effects, which should be confined to `main` or other explicitly IO-typed functions; recursion and `do`-expressions can still be freely used inside IO actions. On the output side, the lecture surveys `putChar`, `putStr`, `putStrLn`, and `print` (noting that GHCi automatically applies `print` to evaluated results), and mentions that output may be buffered, potentially delaying display until a full line is ready. On the input side, it covers `getChar`, `getLine`, `getContents`, and `interact`, which differ in how much input they consume — a single character, one line, or the entire input stream until EOF. `getContents` is highlighted as a lazy way to read all input, processing it only as needed, and `interact` is presented as a concise way to apply a `String -> String` transformation directly to the whole input stream.

The lecture then turns to file I/O. At the simplest level, `readFile`, `writeFile`, and `appendFile` treat text files as plain strings for basic use cases. For more control, the `System.IO` module provides a handle-based approach: `openFile` and `hClose` for manual resource management (following an open–work–close pattern), and `withFile` for automatically ensuring resources are cleaned up via a callback. Handle-specific functions like `hPutStr` and `hGetLine` are shown to underlie the standard I/O functions — `putStr` and `getLine`, for instance, are ultimately just these handle functions applied to `stdout` and `stdin` respectively. A running example — reading text and converting it to uppercase — is used to demonstrate all three levels of file handling, from the simplest high-level functions to explicit handle management to the safer `withFile` pattern, all relying on the `IO` monad and `do`-notation to sequence operations.

Finally, the lecture addresses buffering as a performance mechanism that reduces the number of system calls by temporarily storing data before it is actually written or read. Buffering behavior is configurable via `BufferMode` (`NoBuffering`, `LineBuffering`, `BlockBuffering`), controlled with `hSetBuffering` and `hGetBuffering`, and buffers can be explicitly flushed with `hFlush`. Examples show disabling buffering on `stdout` for immediate output, and on `stdin` (combined with `hSetEcho`) for immediate, character-by-character, unechoed input. For large files or binary data, the lecture recommends specialized modules such as `Data.ByteString` or `Data.Text` instead of the basic `String`-based functions.

**Overall takeaway:** Haskell reconciles purity with practical I/O by modeling side effects monadically — conceptually threading a "world" state through a chain of actions via `(>>)` and `(>>=)` — while `do`-notation provides convenient, but purely syntactic, sugar for this threading that desugars into ordinary functional code. This monadic machinery underlies all of Haskell's I/O facilities, from basic console output/input functions to file handling and buffering control, all of which are ultimately built from the same small set of composition primitives, with laziness and explicit resource/buffer management layered on top for practical use.
